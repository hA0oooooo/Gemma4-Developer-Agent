##### 证据标准

修复收益：除被检验变量外，其余模型、环境、提示和预算保持相同的对照中增加独立审核通过任务；检验预算本身时明确其质量与成本变化，不能把缺包、超时、空补丁或修改测试算作成功

效率收益：在修复质量不退化的前提下，降低模型调用、真实轨迹交互、token 或墙钟时间；至少在两个任务、两个种子上重复，分别报告冷启动、任务原生耗时和完整评测时间。task_seconds 与历史 agent_seconds 均来自原生 TaskResult，包含原生验证，不是纯 Agent 推理时间

token数字统一指当前Harness trace记录的usage，调用次数须注明是原生TaskResult计数还是记录的事件，不直接等同供应商全额账单或全部HTTP尝试。原生CPU fixture已证实计数边界：2次主回复加2次后台摘要共4次自造模型调用，session存2条摘要，但原生Trace回调未收到它们，记录20而已知fixture总计40个usage单位；这不是实际Gemma案例漏计50%的估计。另重开八份生成对照Trace，各step usage与final_metrics相符、没有记录到摘要事件，不能由零事件推断从未发生摘要；缺失成本不补零、不虚构，不把38.6%等Trace下降直接解释成总计费同幅节省。原结果/门槛不改，限定其可观察指标；完整进程墙钟另含实际初始化、摘要、原生/独立验证和关闭。证据usage-scope-qualification.json及qualify_usage_scope.py，不增加优化点

当前本地runner共同使用既有ContextCacheConfig与EventsCompactionConfig，后者interval=15、overlap=2、threshold=14336、retention=5；新组没有将这些设置作为干预。这些值与本地保存的官方指南7.2默认值一致，不是本轮私自新增的压缩开关；但实际隐藏评分版本和现场行为未直接验证。此类Harness设置不由submission控制，局部对照只在该共同环境中成立，不能直接声称移植到官方评分后仍保留收益；不将事件压缩配置本身计入优化点

单项只有一个任务通过时记初步信号；仅 schema、单元测试、模拟模型或合成组件测试通过时记组件验证，不自动计为真实任务策略收益

消融可确认一个已经存在的合适默认值，例如保留思考容量或精简编辑回执；须满足同样的真实质量与效率标准，并确认该变量实际作用，同一机制的正反方向只计一次，不将“学到负面教训”本身计为性能收益

低预算旧 baseline 是历史对照，不足以单独证明高预算候选的架构收益；不同工具的预算计数也不等于相同真实工作量

独立集只用于冻结候选验收；被用于语义失败分析或反复调参的任务转为开发集。当前参数筛选使用 requests_7205 与 fastapi_9555，后者从旧验证集转入开发，不再称为新候选的独立证据；rich_3472、rich_4006 也已因既往失败分析转为开发，现在加入同预算基线，不能再次称为独立集

省下的时间没有被存起来，而是被转移。无效参数步 10 升到 33（3.3 倍），失败的 edit/write 调用 15 升到 35（2.3 倍），撞上 24 次调用上限而终止的 run 4 升到 6，记录 token 反升 8.6%（每条 nudge 都要重发不断增长的上下文）。这正是预注册 design_risks_recorded 里写下的风险：外部审计报告低于约 2048 时 heredoc 编辑与工具调用 JSON 可能被截断并被当作纯文本丢弃，而 1536 在该线以下。gate4 按其冻结口径只看“成功编辑数不降、空补丁不升”，因而通过，但它没有度量截断造成的失败调用增量，这一点作为门禁口径的缺口如实记录。

由此得到的主结论是：时间确实是唯一具约束力的预算，截断确实能把真实超时转成干净收尾并降低墙钟，但“把超时转成干净收尾”并不等于“把超时转成解决”。因截断而干净收尾的 run 与因预算充足而干净收尾的 run 不是同一对象，在自然干净收尾上测得的 54.6% 解决率不会迁移到上限造成的干净收尾上。约束没有消失，只是从解码时间挪到了调用次数与畸形调用恢复。推论：nudge 机制真实且触发成本低，但单靠它救不回质量，17 次触发、12 个 run 仍净丢两题；任何靠缩短轮次换时间的后续候选都要预期在调用次数上付账，因为 24 次调用与 40 轮上限会接着成为新的约束。

##### 源码审核字节身份索引与标注词表漂移

建索引时暴露一个此前未被注意的方法学问题：**各研究的标注词表发生了漂移**。同一含义在不同封签里写作 source_supported（54 次）与 supported（23 次），需求缺口写作 known_contract_gap（6 次）、narrow-green-but-source-gap（1 次）与 narrow_green_source_gap（1 次）。直接按字符串比较会把纯词表差异误判为实质分歧：初版工具报出 8 个"审核结论互相矛盾"的补丁身份，归一化后其中 3 个（fastapi_5624 的 1ebac05c31ee、fastapi_9425 的 32f2a37b4b1a、rich_4077 的 86e4ed0ac951）其实所有研究结论一致，只是用词不同。因此工具先按固定阶梯 excluded < gap < uncertain < supported 归一化，再检测真实分歧，任何残余分歧一律解析到**对候选最不利**的那一档并显式标记，绝不取平均或取最有利值。全部 8 种出现过的结论字符串都已映射，无未识别词表。

继续逐环节复核冻结分析脚本的未验证假设，又发现两处实现错误，均在**任何结果出现之前**修正（当时 replicate 1 完成 27/60，report.json 不存在，未计算任何聚合指标、未查看任何逐题结果、合并分析未运行）。

其一，单侧精确 McNemar **不是方向性的**。原实现取 k = max(b, c)，即无论方向都返回较小的那一尾。预注册判据 2 是方向性单侧检验"候选优于对照"，其精确 p 应为 P(X ≥ b)，X ~ Binom(b+c, 0.5)，b 为仅候选修复的不一致对数。取 max() 的后果是：**当候选显著更差时反而给出极小 p 值**，判据 2 会在一个强负结果上通过。数值证明：b=2、c=20 时旧实现给 p=6.1e-05（会通过 ≤0.05），正确的方向性形式给 0.999995；b=0、c=10 时旧给 9.77e-04（会通过），正确给 1.000000。而当 b>c（候选更好）时两种形式完全一致。也就是说该 bug **只会制造强负结果上的假通过**，不会制造假阴性。已改为 P(X ≥ b)，并把方向写入输出 JSON。

##### 修复会在 replicate 2 触发的端口分配冲突

对链式脚本做启动前预检时发现一个会**让第二个复现崩溃**的真实缺陷。src/evaluate_development.py 为每张 GPU 分配一个模型服务端口，取值是 args.port + index，因此以 --port 8110 启动的两分片运行会**同时占用 8110 与 8111**。ss -ltnp 实测确认：127.0.0.1:8110 由 pid 288310 持有、127.0.0.1:8111 由 pid 288311 持有，二者都是 replicate 1 的 owner 288175 的子进程。

而链 v2 给 replicate 2 分配的正是 --port 8111，即 replicate 1 第二个分片已占用的端口。由于复现是串行的，时序上通常能错开，但 vLLM worker 退出后端口释放并非瞬时，因此 replicate 2 存在绑定失败并崩溃的真实风险。按基础设施条款，一次崩溃的复现要付出约三小时的同种子重跑代价，若同一复现二次失败则协议必须停止并上报。

发现方式是**把四个预定端口逐一用 ss -ltn 做启动前检查**，而不是假设每次运行只占一个端口：在只有 replicate 1 运行时 8111 已显示占用，这才暴露出按 GPU 递增的分配方式。

修复：链升级为 v3（/tmp/chain8c.sh，日志 /tmp/chain8c.log，pid 320058），端口改为间隔 10——s1 保持 8110-8111 不动，s2 用 8120-8121、s3 用 8130-8131、s4 用 8140-8141，远大于两分片所需的两个连续端口；并新增 ports_free() 在每次启动前检查该运行将要绑定的**每一个**端口，若仍被占用则等 5 分钟重试，而不是复用在用端口或随意另选。链 v2（pid 291771，仅处于 sleep 循环）已干净停止；**replicate 1 未受影响**——换链后确认 owner 288175 仍存活于 1:32:16，且其两个模型服务仍分别持有 8110 与 8111，因为 owner 由 launch_guard 以 start_new_session 启动，替换链无法扰动它。

这不是协议变更：端口属基础设施。冻结协议固定的是包内容、30 道题、四个种子 20261104 至 20261107、两分片配置、判决规则与全部门槛，这些一律未动。修复前已核验链的种子算术与预注册完全一致（[20261104, 20261105, 20261106, 20261107]），各复现目录的 replicate 标记与父文档声明的种子列表相符，四份包逐字节等同于父目录（control 等于已评分 0.17 ZIP，candidate 仅 eval_config.yaml 不同），且四组端口两两不相交。证据固化于 handover-20261104/chain-port-allocation-fix.json。
